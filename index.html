业务背景与诊断

基于真实业务数据与跨角色访谈，量化瓶颈分布、还原端到端时长、评估 ROI 可行性。

🏭

业务复杂度

12 目标语种（CJK、RTL、小语种），覆盖相机固件、App、Web、运营活动四条产品线。单条文案流转 PM、Copywriter、运营、研发四个角色。

📊

基线数据分析

采集 2026.04–06 共 133 个需求批次数据。5 月日均 2.06 批次，加急率 27.8%，每 4 个需求中有 1 个触发紧急通道。

🔍

访谈发现隐性瓶颈

跨角色访谈识别出 SOP 流程中未计入的两个隐性环节：Key 命名（PM 额外耗时约 0.5 天）与 TMS 平台上传（运营额外耗时 0.5–1 天）。

⏱️

端到端时长还原

还原端到端瀑布图：基线 10–14 自然日（含隐性环节）。EN 校对串行 3 天、12 语种批量等待 5–10 天为核心瓶颈。

诊断结论：五大瓶颈

① EN Draft / Proofreading 串行阻塞（2–3 天） → ② 12 语种翻译批量等待（5–10 天） → ③ 占位符与术语一致性依赖人工校验（周均 1–2 次返工） → ④ Key 生成为隐性环节（未纳入 SOP，占用 PM 与工程人力） → ⑤ TMS 平台上传耗时（登录失效、分片上传、双平台双轨）

02

三层 Multi-Agent 架构

Plan-Act-Eval 三层解耦，各层独立演进、独立评测。TMS Uploader 补齐端到端闭环。

PLAN 层

Orchestrator — 任务路由与分流

解析需求表行 → 判断是否带 Key（否则路由到 Key Generator）→ 识别文案类型（按钮/引导/错误/确认等 7 类）→ 按语种与文案复杂度分流模型。

ACT 层

6 个 Worker 并行协作

Key Generator Glossary Retriever (RAG) Translator Cultural Adapter Format Normalizer TMS Uploader

Key Generator 为无 Key 的纯文案自动生成符合 snake_case 规范的 Key（历史 333 条 Key 反推命名规范）。 Translator 按语种切换模型，注入 Glossary 强约束 + 占位符保护 + 字符限制。 Cultural Adapter 处理 RTL 布局、日韩敬语、长复合词压缩。 Format Normalizer 负责占位符还原、JSON 打包、双平台（iOS/Android）双轨结构。

EVAL 层

双重评测 — Rule Validator + LLM-as-a-Judge

硬规则校验（占位符正确性、字符限制、Key 一致性、品牌术语未被翻译）+ 软质量评分（准确性、流畅性、品牌一致性三维度）。 低分自动入 Badcase Logger → 月度回流到术语表与 Prompt 资产库。

UPLOAD 层

TMS Uploader — 端到端闭环

多项目路由、双平台自动上传、登录失效检测与告警、指数退避重试、上传后回查验证。 将"翻译完成"延伸到"平台已上传、工程可取词"才算端到端。

架构决策：Key Generator 不采用 PAE 三层拆分的依据

Key 生成为单步 LLM 调用（模块前缀识别 + 命名生成 + 多样性输出），拆分为 Plan-Act-Eval 三层将增加延迟与错误传播链，属过度设计。 合规校验统一归入主 Eval 层，与 Translator 共享规则，实现单处维护、多处复用。

03

评测体系

Golden Set 分层抽样构建、LLM-as-a-Judge 三维度评分、Stress Test 验证 Judge 区分能力。评测体系自身需经对标验证。

🎯

Golden Set v0

30 条样本，采用 类型分层（7 类）+ 难度加权（7 标签，满分 13）+ 对照组保留（8 条） 三层抽样设计。高难度条目占比 73%，设计目标为放大模型间差异，非拟合平均分布。

⚖️

LLM-as-a-Judge

三维度评分：Accuracy（准确性）、Fluency（流畅性）、Brand Consistency（品牌一致性）。目标与人工盲评 Pearson 相关性 ≥ 0.85。

🧪

Stress Test

9 类合成缺陷样本（占位符丢失、Glossary 违规、过度扩写等），验证 Judge 对已知缺陷的识别能力。9/9 = 100% 通过率。

🔄

Judge v1 → v2 迭代

v1 存在 grade inflation（均值 14.83/15，方差不足）。v2 引入 CoT reasoning 与伪人工锚点对齐，Accuracy 维度 Pearson 相关性从 0.10 提升至 0.55。

Judge 自身的对标验证

LLM-as-a-Judge 作为评测工具，自身需经过校准。采用三层验证： ① 伪人工锚点：基于硬规则模拟评分作为下限基线（Pearson 0.55）→ ② Stress Test：合成已知缺陷验证 Judge 区分能力上限（9/9 通过）→ ③ 真人工对齐（规划中）：Copywriter 盲评作为黄金标准，目标相关性 ≥ 0.85。

v3 核心方法：决策优先级序言（Decision-Priority Preamble）

v2 质量退化的根因为规则间冲突：主动语态与信息密度互斥、占位符括号化与简洁性互斥。 v3 在 System Prompt 头部引入 6 条优先级序（Glossary > 占位符 > 信息保真 > 主动语态 > 结构匹配 > 括号化场景限定）， 并新增 4 个反例 Few-shot（WRONG → RIGHT + WHY），完整修复 4 处回归。 结论：Prompt 质量上限不取决于规则数量，取决于规则间的优先级排序。

第一圈：v1 → v2
v1 跑批结果逐条对照 Ground Truth，Badcase 五分类

反推 Glossary v1（80+ 术语，品牌 / 功能 / 硬件 / 运营四类），重写 Prompt v2。业务术语正确率 0/5 → 5/5，Exact Match 47% → 57%。

第二圈：v2 → v3
识别 v2 引入的 4 处规则冲突回归

抽象决策优先级序言工程原则，补入 4 个反例 Few-shot。Exact Match 57% → 70%，回归清零，占位符保留率维持 100%。

关键发现：低成本模型在该任务上全维度领先或持平

Model D (Tier-3) Judge 总分 14.60，高于 Model A (Tier-1) 0.10 分，P50 延迟低 25%，成本仅 Model A 的 1/7。 结论：在短文本 + 强 Glossary 约束 + Few-shot 锚点的任务条件下，Prompt 工程对模型 raw 能力差异的消弭效应显著， 高成本模型未带来对应的质量边际收益。

3-Tier 路由策略

Tier A（主力，90%）：Model D，覆盖所有 Glossary 已覆盖的标准 UI 文案

Key Generator & TMS Uploader

针对访谈识别的两项隐性瓶颈，分别以 LLM 生成与 API 逆向工程解决，补全端到端链路。

🔑

Key Generator

基于 333 条历史 Key 反推命名规范（27.6% 为不合规 Key：含空格、特殊符号、语义偏移）。 POC 30 条评测结果：snake_case 合规 100%、模块前缀路由 100%、占位符防泄漏 100%、长度合规 100%、多样性指数 0.52。 单 LLM 调用完成生成，合规校验共享主 Eval 层。

📤

TMS Uploader

经 3 次架构迭代：v0.1 假设存在标准 API → v0.2 发现仅 IM Bot 通道 → v0.3 前端 Bundle 逆向还原 30 个 HTTP 端点 → v0.4 实现 4 项目全覆盖端到端写入。累计识别并规避 31 个工程认知偏差 （后端字段命名不一致、node_id 全局递增、跨项目 ID 池共享等）。
